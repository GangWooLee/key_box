# 버그 수정 워크플로우

## Phase 1: 근본 원인 추적

수정을 구현하기 전에 반드시 전체 실행 경로를 추적합니다.

1. **증상 파악** — 사용자가 보는 실패 동작 정리
2. **실행 경로 추적** — 사용자 액션 → 라우트 → 컨트롤러 → 모델 → 뷰 → 클라이언트 응답
3. **분기점 식별** — 경로의 모든 조건문, rescue 블록, 리다이렉트 지점 표시
3.5. **경계 지점 증거 수집** — 각 컴포넌트 경계에서 실제 데이터 확인
   - Controller → Service: params 값과 반환값
   - Service → Model: 쿼리 결과와 예상값 비교
   - Model → Database: `rails dbconsole` 또는 `ActiveRecord::Base.connection.execute`로 확인
   - 추측이 아닌 **실제 값**을 기록한 후 다음 단계 진행
4. **근본 원인 확정** — 동작이 예상과 갈라지는 정확한 지점 설명

**출력 형식**:
```
증상: [사용자가 보는 것]
실행 경로: [A → B → C → ❌ D (여기서 갈라짐)]
경계 증거: [B→C 경계에서 실제 값: X, 예상 값: Y]
근본 원인: [왜 D에서 실패하는지]
```

## Phase 2: 수정 구현

1. **최소 범위 수정** — 근본 원인에 가장 가까운 레이어에서 수정
2. **rescue 배치 규칙** — 예외 발생 메서드 내부에 rescue. 외부 컨트롤러 감싸지 않기
3. **제어 흐름 확인** — rescue 후에도 redirect/render가 정상 완료되는지 확인
4. **관련 파일 모두 수정** — 모델, 마이그레이션, 컨트롤러, 테스트 동시 변경

### 3회 실패 시 중단 규칙

같은 버그에 대해 3회 이상 수정을 시도해도 해결되지 않으면:

1. **즉시 중단** — 추가 수정 시도 금지
2. **시도 정리** — 각 시도의 가설, 변경 내용, 실패 이유를 표로 정리:
   ```
   | 시도 | 가설 | 변경 | 실패 이유 |
   |------|------|------|----------|
   | 1 | ... | ... | ... |
   | 2 | ... | ... | ... |
   | 3 | ... | ... | ... |
   ```
3. **아키텍처 재고** — 증상이 아닌 구조적 원인을 탐색
   - 설계 전제가 잘못되었나?
   - 다른 계층에서 해결해야 하나?
   - 접근법 자체를 바꿔야 하나?
4. **사용자 보고** — 상황 정리 + 대안 2-3개 제시

## Phase 3: 검증

```bash
bin/rails test                # 전체 테스트
rubocop                       # 린트
```

1. 전체 테스트 통과 확인
2. 클라이언트-서버 상호작용 버그인 경우, 프로덕션에서 확인할 항목 목록 제시
3. 커밋 메시지: `fix: <근본 원인과 수정 설명>`

### 이미지/미디어 관련 추가 검증 (해당 시)

이미지 업로드, AI 이미지/비디오 생성, base64 처리 관련 버그인 경우 추가 확인:

- [ ] base64 Data URL 형식 + Magic Bytes 검증 통과
- [ ] modality 설정 확인 (이미지 생성: `["image"]` only, NOT `["image", "text"]`)
- [ ] 비동기 처리 흐름 검증 (Turbo Stream 도착 → 비디오 로드 대기 → UI 업데이트)
- [ ] 모델 검증 한도 vs 실제 데이터 크기 일치 (base64 ≈ 원본 × 1.37)

## 체크리스트

- [ ] 수정 범위 최소화 확인
- [ ] rescue 블록이 최소 범위에 배치됨
- [ ] 전체 테스트 통과
- [ ] 프로덕션 검증 항목 제시 (해당 시)
