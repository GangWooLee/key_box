# 보안 설계

> 용어(PDK·MEK·AAD·sidecar 등)는 [GLOSSARY.md](GLOSSARY.md)에, 공격 경로별
> 전수 판정(33경로)은 [security-threat-model.md](security-threat-model.md)에 있다.
> 이 문서는 그 결과를 사람이 읽는 설계 서사로 정리한 것이다.

## 무엇을 상대하는가

시크릿 매니저의 보안 문서는 "무엇을 막는다"보다 "누구를 상대한다"에서 시작해야
한다. 이 앱은 세 부류의 공격자를 상정한다.

1. **물리 접근자** — 잠금 안 된 Mac 앞에 앉을 수 있는 사람.
2. **상주 멀웨어** — 같은 사용자 권한으로 실행 중인 악성 프로세스.
3. **디스크 이미지 확보자** — 백업·도난·Time Machine으로 파일만 손에 넣은 사람.

그리고 한 가지 원칙이 모든 방어 결정을 지배한다: **사용자에게 마찰을 추가하는
방어는 도입하지 않는다.** 2차 비밀번호, 반복 재인증, 매 작업 확인창 같은 것은
보안을 올리는 것처럼 보이지만 실제로는 사용자가 도구를 우회하게 만든다 —
시크릿이 다시 메모장으로 돌아가면 모든 암호화가 무의미하다. 그래서 이 문서의
모든 방어는 "사용자 추가 행동 0"을 통과한 것들이다.

## 키는 어디서 오고 어디에 있는가

모든 비밀은 마스터 비밀번호 하나에서 시작한다. 비밀번호는 어디에도 저장되지
않는다 — 저장되는 것은 파생 결과뿐이다.

```
마스터 비밀번호
   │  PBKDF2-HMAC-SHA256 × 600,000회  (salt는 sidecar에)
   ▼
  PDK ──HKDF("keybox/v1/dbkey")──▶ dbKey ──▶ SQLCipher가 DB 파일 전체 암호화
   │
   └──HKDF("keybox/v1/kek")────▶ KEK ───▶ MEK를 wrap하여 DB 안에 보관
                                            │
                                            ▼
                                     MEK ──▶ 각 시크릿 값을 AES-256-GCM 암호화
```

이 구조에서 눈여겨볼 것은 두 가지다.

**왜 MEK를 따로 두는가.** 시크릿 값을 비밀번호 파생 키로 직접 암호화하면
비밀번호를 바꿀 때마다 전체 데이터를 다시 암호화해야 한다. MEK를 중간에 두면
회전은 "MEK를 새 KEK로 다시 감싸기 + DB rekey"로 끝난다. 값은 그대로다.

**왜 HKDF로 가르는가.** dbKey와 KEK가 같은 PDK에서 나오지만, 도메인 라벨이
다르므로 하나를 확보해도 다른 하나를 역산할 수 없다. DB를 여는 능력과 MEK를
푸는 능력이 분리된다.

파생의 유일한 디스크 흔적은 sidecar(`key_box.vault.json`)의 salt와 KDF
파라미터다. salt는 비밀이 아니고(용어집 참조), KDF 파라미터는 코드의 상수와
다르면 손상으로 취급해 다운그레이드 공격을 거부한다.

## 파일을 훔쳐가면 무엇을 얻는가

**DB 파일: 사실상 아무것도.** SQLCipher가 파일 전체를 암호화하고,
`plaintext_header_size=0` 하드핀 덕에 'SQLite format 3' 매직 바이트조차 없다 —
파일이 난수와 구별되지 않아 KeyBox의 DB인지조차 확증할 수 없다. wrappedMek,
스키마, 메타데이터 전부 암호문 안쪽이다. 페이지마다 HMAC-SHA512 무결성 검증이
붙고, rekey 시 WAL 체크포인트로 옛 키 페이지의 잔존을 차단한다.

**백업(.kbx) 파일: 헤더만.** 포맷 v3부터 records 배열의 이름·종류·서비스·환경·
메모·태그를 값과 동급으로 MEK-GCM 암호화한다. 평문으로 남는 것은 키 파생에
필요한 헤더(salt·wrappedMek·KDF 파라미터)뿐이다. v2까지는 메타데이터가
평문이었다 — 시크릿 인벤토리 지도를 무비용으로 내주는 실격차였고, 2026-07-16
위협모델이 이를 유일한 A-필수 격차로 판정해 즉시 닫았다. v1·v2 아카이브는
가져오기만 지원한다(내보내기는 항상 v3).

**남는 정직한 사실 하나**: 두 파일 모두 최후의 방어선은 비밀번호 엔트로피 ×
PBKDF2 600k 비용이다. PBKDF2는 메모리-하드가 아니어서 GPU 병렬 공격에
상대적으로 약하다 — Argon2id 이관이 무마찰 강화 후보로 장부에 있다(아래 잔여
위험). 최소 12자 강제가 하한을 받친다.

## 옮겨 심기와 되돌리기

파일을 못 읽는 공격자의 다음 수는 암호문을 조작하지 않고 *재배치*하는 것이다.
이 앱은 각 시크릿 암호문을 자기 행 id와 recordVersion에 AAD로 봉인한다.

- 다른 행의 암호문을 옮겨 심으면 → id 불일치 → GCM 태그 검증 실패.
- 백업에서 옛 값을 그 자리에 되돌리면 → version 불일치 → 실패.

값을 수정할 때마다 recordVersion이 오르고 새 버전에 재봉인되므로, "비밀번호
유출 전의 옛 값으로 조용히 롤백"이 성립하지 않는다. 생성 시점에는 행 id가
아직 없으므로, 자리표시자 행을 먼저 넣어 id를 받고 그 id로 암호화해 채우는
2단계를 한 트랜잭션으로 묶는다 — 값 없는 자리표시자가 밖으로 새지 않는다.

한계도 있다: AAD는 한 DB *안*의 재배치만 막는다. (DB, sidecar) 파일 쌍을
통째로 과거 스냅샷으로 바꿔치우는 전체 롤백은 탐지하지 못한다 — 외부 단조
카운터(Keychain 세대 번호)가 후보로 장부에 있다.

## 메모리에서는

MEK는 잠금 해제 동안에만, `AuthUnlocked` 상태 객체 안에만 존재한다. 잠그면
0으로 덮어쓴다. PDK·KEK·salt 같은 중간 재료는 쓰는 함수의 `finally`에서
zero-out한다. 복호화된 값은 로그에 찍지 않는다 — 로깅은 문맥(id, 동작)까지만.

정직한 한계: **Dart String은 불변이라 zero-out이 원리적으로 불가능하다.**
reveal한 평문과 dbKey의 16진수 문자열은 GC가 회수할 때까지 힙에 남는다. 잠금이
세션을 닫으면 참조가 끊겨 회수 대상이 되지만, "즉시 0"은 바이트 배열에만
가능하다. 이것이 잠금을 빨리 거는 것(auto-lock)이 메모리 방어의 실질 수단인
이유다 — 유휴 15분(설정 가능) 타이머가 돌고, 포인터·키 입력이 리셋한다.

## 화면·클립보드라는 옆문

값은 기본 마스킹이고 reveal은 명시적 행동이다. 마스킹 점 개수는 고정이라
길이도 새지 않는다. 시크릿을 전환하거나 편집하면 재마스킹된다.

복사하면 30초 뒤 클립보드를 자동으로 비우고, 남은 시간을 조용한 카운트다운
링으로 보여준다. 클립보드 값에는 `org.nspasteboard.ConcealedType` 마킹을 붙여
협조적인 클립보드 매니저(Paste, Maccy 등)의 영구 저장·동기화를 억제한다.

여기서도 정직하게: 클립보드는 OS 공유 자원이라 붙여넣기가 가능하려면 평문이
30초간 존재해야 하고, 그 창 안의 폴링 멀웨어는 막을 수 없다. 이것은 복사
기능의 본질적 비용으로 수용했다. 화면 캡처 차단(`NSWindow.sharingType`)과
잠금 시 클립보드 소거는 방어심층 후보로 장부에 있다.

## 하지 않기로 한 것들

**2차 비밀번호 — 도입 안 함.** 확인 비밀번호, 작업별 재인증 따위는 사용자를
도구 밖으로 밀어낸다. 이 결정은 요구사항이다(PRD 참조).

**생체 인증·Keychain 봉인 — 현재 없음.** Touch ID 자리는 비활성 표시만 있다.
키 재료가 디스크·Keychain 어디에도 없다는 것은 at-rest 관점에서 순이득이다 —
앱 컨테이너를 통째로 가져가도 키 재료가 0바이트다. 편의 기능으로서의 생체는
Developer ID 서명(코드서명 앵커) 이후에나 안전하게 붙일 수 있다.

**네트워크 — 권한 자체가 없음.** Release entitlements에 네트워크 항목이 없다.
유출 채널을 코드 리뷰가 아니라 OS가 막는다.

## 잔여 위험 장부 — 알고 수용한 것들

위협모델 33경로 중 방어 충분 8, 실격차였다가 닫힌 것 1(백업 메타 → v3),
나머지는 아래처럼 **알고 수용**했다. 수용에는 각각 이유가 있다.

| 잔여 위험 | 왜 수용했나 | 언제 닫히나 |
|---|---|---|
| ad-hoc 서명 → 디버거 부착·메모리 덤프 가능 | 개인 dogfood 단계. Developer ID 서명은 배포(B) 작업 | B: Developer ID + 공증 |
| 잠금 해제 후 자리 비움 (기본 15분 창) | 유휴 타이머가 커버. 화면잠금 연동은 네이티브 채널 필요 | 방어심층: macOS 화면잠금 알림 훅 |
| 클립보드 30초 창 내 폴링 | 복사 기능의 본질. ConcealedType+자동소거가 무마찰 상한 | 부분: 잠금 시 소거 추가 |
| 화면 캡처·AX 트리에 reveal 값 노출 | TCC가 1차 게이트. sharingType은 화면공유 UX 트레이드오프 | 방어심층: sharingType 토글 |
| KDF가 메모리-하드 아님 (PBKDF2 600k) | OWASP 하한 충족. Argon2id 이관은 재키잉 마이그레이션 동반 | 강화: Argon2id 이관 |
| 마이그레이션 실패 시 평문 잔해 창 | 성공 경로는 자체 정리. 실패 창은 부팅 청소 미구현 | 방어심층: 부팅 시 잔해 스윕 |
| 평문 시대의 외부 백업 스냅샷 (Time Machine 등) | 앱이 OS 백업 히스토리를 파기할 수 없음 — 소급 불가 | 불가. 고지만 가능 (신규 볼트는 태생부터 암호화라 미발생) |
| 비밀번호 분실 = 데이터 손실 | 복구 코드 미구현. 뒷문 없는 설계의 대가 | B: 복구 코드 |

이 장부는 축소 없이 유지한다. "무엇을 막는지"만 나열하고 "무엇이 뚫리는지"를
숨기는 보안 문서는 독자를 속이는 문서다.

## 이 설계를 어떻게 믿는가

주장이 아니라 게이트로 믿는다.

- **암호화는 실기로만 증명된다.** macOS의 `flutter test`는 Apple 시스템
  libsqlite3를 로드해 `PRAGMA key`를 조용히 무시한다 — 단위 테스트의 초록은
  암호화를 전혀 증명하지 못한다. 실제 SQLCipher 왕복(무키 열기 실패, 정키 열기
  성공, 회전, 백업 복원)은 `integration_test/`가 실앱으로 증명하고, CI가 매
  푸시마다 macOS 러너에서 돌린다.
- **게이트는 뮤테이션으로 실증한다.** 새 방어·테스트를 넣을 때 결함을 일부러
  주입해 게이트가 RED가 되는 것을 확인한 뒤에만 채택한다. 통과만 확인한
  게이트는 장식이다.
- **위협모델은 공격자 관점으로 열거했다.** "우리 방어 목록"이 아니라 "평문 또는
  MEK를 얻는 경로"를 3개 위협모델 × 6개 카테고리로 전수 열거하고, 각 경로를
  반증 시도(3-렌즈 적대 검증) 후 판정했다.
